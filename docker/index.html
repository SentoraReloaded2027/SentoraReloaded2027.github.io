Sentora 2027 in Docker

A complete hosting server (websites, mail, DNS, FTP, databases) in one container, on a Linux host with Docker. GitHub installs, checks and smoke-tests the image before every release is published.

Run it

Put in your panel's address and your email, then run this as root:

docker run -d --name sentora --hostname panel.example.com \ -e SENTORA_EMAIL=you@example.com -e TZ=America/Chicago \ --restart unless-stopped --cgroupns=private --security-opt writable-cgroups=true \ --tmpfs /run --tmpfs /run/lock --cap-add NET_ADMIN -v sentora-backup:/backup \ -p 80:80 -p 443:443 -p 21:21 -p 61000-61099:61000-61099 -p 25:25 -p 465:465 -p 587:587 \ -p 110:110 -p 143:143 -p 993:993 -p 995:995 -p 4190:4190 \ ghcr.io/rustus/sentora2027

Watch it install (about five minutes in our tests), then read the passwords:

docker logs -f sentora
docker exec sentora cat /root/passwords.txt

Then log in at https:// your panel's address as zadmin, and check the server with docker exec sentora sentora-post-install-check.

Its own passwords, every time

Nothing of Sentora is baked into the image: it holds Debian 13, systemd and Sentora's own installer. The first time a container starts, it installs Sentora, so every container gets its own passwords, keys and certificate. Passwords never reach docker logs; the test before each release checks that too.

No --privileged

OptionWhy
--hostnameThe panel's address. Its DNS A record should point at the host.
--cgroupns=private --security-opt writable-cgroups=truesystemd inside manages its services. The container gets its own branch of the host's cgroups and can write only there.
--cap-add NET_ADMINfail2ban can ban addresses, in the container's own network only.
-v sentora-backup:/backupThe nightly full backup goes here, and stays on the host when the container is removed.
-p ...Web, FTP (passive ports 61000–61099 in a container), mail, IMAP, POP3 and ManageSieve. Add -p 53:53/tcp -p 53:53/udp when this server is the DNS server for its domains.

Backups that outlive the container

With the sentora-backup volume, the first start switches on the nightly full backup into it: every account's files, every database, the mailboxes, and the panel's settings and keys, 14 nights kept. If the container is ever removed, start a new one with the same --hostname and volume; its log says it found a backup, and Admin > Backup Config > Restore brings everything back. Before each release, GitHub does exactly that and checks that a website comes back the same.

Good to know

  • Treat the container as the server: websites, mail and databases live inside it. Restarts and host reboots keep everything; docker rm deletes it (the backup volume stays).
  • Updates happen inside: docker exec -it sentora sentora-update for the panel; Debian's security updates install themselves.
  • AppArmor: Docker's own profile confines the container; Sentora's AppArmor rules apply on a plain server only. For hosting other people's websites, a plain Linux server keeps every guard on.
  • Tested on GitHub with Docker 29 on a Linux host with cgroup v2. Every option explained: In Docker, in the README.
